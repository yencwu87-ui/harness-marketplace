# Harness audit

1. Run the audit script that sits next to this file, against the project root (read-only, no dependencies):
   ```bash
   python3 "<this skill's base directory>/scripts/audit.py" . --md
   ```
2. Show the user the score and the table. Then, in plain words, list the **critical** gaps first (marked ❌ with weight 3), then the rest, grouped by area.
3. For each gap, say the smallest fix. If the `harness-init` plugin is installed, say which gaps `/harness-init:init` would close.
4. Do not change any files during an audit. Offer to fix; wait for a yes.

Notes for the user:
- A pass means the harness piece exists in files, not that it works. The proof is running the checks.
- `--json` gives machine-readable output for CI; `--strict` exits 1 when any critical check fails; `--min 70` fails below a score.
- Areas 1–4 (instructions, state, verification, scope) follow WalkingLabs' Learn Harness Engineering course. Areas 5–7 (safety guardrails, evals and red team, cost and context) are what production teams add on top.
- Other frameworks: the audit detects LangGraph, OpenAI Agents SDK, CrewAI, Strands, Google ADK, Microsoft Agent Framework and the Claude Agent SDK from the repo's imports (read, never run) and checks their own guard mechanisms for G1–G3. For assess-only frameworks, what `docs/IMPACT.md` states counts as DECLARED, at half weight.
- Credit only what is proven: a guard counts only when it is attached to the scored agent and tool. A narrower, conditional or unreadable guard is UNRESOLVED with the reason, never VERIFIED. A capability the audit cannot rule out is reported, never assumed absent.
- From 1.4.5, a code refusal (inside a tool, or in a framework hook) earns credit only through the kit's guard helper (`from kit_guard import refuses`) in the exact shapes below, or in a framework's exact documented contract; hand-written refusals (your own `in` tests, regexes or predicates) are UNRESOLVED with the reason "hand-written refusal: use the kit guard helper to earn credit", even when they are correct. The helper defines the classes it covers (secret, destructive). `audit.py --canonical-forms` prints the same list. Permission rules (Claude Code settings and Agent SDK `disallowed_tools`) follow one standard: a scoped rule covers only its scope. With Claude Code's sandbox, Read deny rules count for Bash only when no command can leave the sandbox (`allowUnsandboxedCommands: false`, no `excludedCommands`) and filesystem isolation is on (no `filesystem.disabled: true`), and a whole-Bash ask counts only with `autoAllowBashIfSandboxed: false`.

## Canonical guard forms

How to earn the points: copy `kit/shared/kit_guard.py` into your repo unchanged, import it exactly as below, make the helper refusal the tool's (or hook's) first statement, and pass the same parameter straight to the capability.

```python
import subprocess
from kit_guard import refuses        # exactly this line; never rebind `refuses`

def run(command: str) -> str:
    if refuses(command):             # first statement; `command` goes nowhere but the shell call below
        return "refused"
    return subprocess.run(command, shell=True, capture_output=True, text=True).stdout
```

In a framework hook, give the helper the framework's tool input and refuse the documented way, for example (Google ADK):

```python
def before_tool(tool, args, tool_context):
    if refuses(args):
        return {"error": "refused by the harness"}
    return None
```
